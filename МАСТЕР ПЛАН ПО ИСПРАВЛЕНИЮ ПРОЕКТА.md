# Мастер план по исправлению проекта

## Назначение документа

Этот документ собирает в одном месте:

- ключевые выявленные проблемы проекта;
- принципы исправления без поломки рабочего контура;
- приоритеты;
- эпики и задачи;
- рекомендованный порядок PR;
- спринтовый план;
- backlog для команды.

Документ рассчитан на использование как рабочий master plan для Jira, Notion, weekly planning и release planning.

---

## 1. Базовые принципы

1. Сначала фиксируем баги тестами, потом меняем код.
2. Сначала исправляем backend-инварианты, потом подтягиваем frontend.
3. Архив должен быть настоящим read-only состоянием, а не просто статусом.
4. Обычные update-эндпоинты не должны выполнять скрытые archive/restore сценарии.
5. Миграции и схему БД меняем только после стабилизации бизнес-логики и покрытия тестами.
6. Производительность и рефакторинг идут после стабилизации доменной логики.
7. Каждый этап закрывается:
   - backend tests;
   - frontend build;
   - regression smoke;
   - обновлением документации, если менялся контракт.

---

## 2. Приоритеты

- `P0` - критично, ломает инварианты, данные или безопасность
- `P1` - важно, ломает рабочие сценарии или сильно мешает эксплуатации
- `P2` - архитектура, производительность, поддерживаемость
- `P3` - документация, polish, вторичный backlog

---

## 3. Ключевые проблемные блоки

### 3.1 Архив и состояния сущностей

- архивные `repair/document/vehicle` сейчас не являются жестко read-only;
- часть рабочих операций всё ещё проходит на архивных сущностях;
- archive/restore логика размазана по обычным `PATCH status`;
- возможны невалидные состояния `primary/source document`.

### 3.2 Review и ручная правка

- review action можно обойти вызовом API вне реальной review queue;
- обычный `PATCH /repairs/{id}` удаляет `checks`;
- helper-логика статусов способна косвенно снимать архив или ломать финальные состояния.

### 3.3 OCR, import и фоновые задания

- нет надежной защиты от дублей активных OCR jobs;
- upload/process/import частично неатомарны;
- часть upload/import flows валидируется неравномерно.

### 3.4 Справочники и архивные хвосты

- архивная техника попадает в operational flows;
- архивные каталоги нормо-часов продолжают участвовать в рабочих сценариях;
- lifecycle архивного сервиса недостаточно формализован.

### 3.5 Аудит

- аудит покрывает не все важные admin-изменения;
- видимость аудита для сотрудника раскрывает лишние события;
- action types и entity types не полностью нормализованы.

### 3.6 Backup и безопасность

- backup/restore и UI обещают не одно и то же;
- после restore frontend может оставаться на устаревшем состоянии;
- смена/сброс/восстановление пароля не отзывают активные JWT;
- отсутствует rate limiting на login/reset.

### 3.7 Схема БД и миграции

- ORM и Alembic не полностью совпадают;
- есть schema drift для import jobs/conflicts;
- relation `repair/document` избыточно циклическая;
- тестовая и production-схемы расходятся по части ограничений.

### 3.8 Frontend и производительность

- frontend держит слишком много duplicated contract types;
- `App.tsx` и orchestration hooks перегружены;
- слишком часто выполняется full bootstrap reload;
- `review queue`, `audit`, `search`, `dashboard` и часть `services` тяжёлые.

### 3.9 Gap по use case и документации

- employee flow уже технически сведен в единый сценарий и закрыт regression-покрытием, но ещё требует финального UAT и business sign-off;
- итоговый final report/export уже собран в UI/XLSX/PDF и описан в sign-off шаблоне, но ещё требует формального согласования на живых кейсах;
- документация, release-gate и sign-off tooling синхронизированы; полный sign-off пакет уже собран в `signoff_artifacts/2026-04-04_report-export-signoff/`, открытым остаётся только формальное business decision по релизу.

## 4. Целевое состояние

После завершения плана система должна соответствовать следующим условиям:

- архив доступен только для поиска, просмотра, экспорта и явного восстановления;
- review нельзя обойти прямым вызовом API;
- обычная ручная правка не разрушает OCR findings и проверки;
- фоновые OCR jobs не дублируются;
- upload/import не оставляют полусохранённые состояния;
- справочники участвуют в рабочей логике только если они действительно активны;
- аудит отражает все важные изменения и не раскрывает лишнее;
- backup/restore предсказуемы для оператора и UI;
- схема БД, ORM и миграции совпадают;
- frontend использует единые contracts и не делает лишние глобальные reload;
- employee use case проходит end-to-end;
- документация соответствует реальному поведению проекта.

## 12. Definition of Done

Любая задача считается завершённой, если:

- есть покрытие тестами или обновлённый regression suite;
- backend tests зелёные;
- frontend build зелёный;
- если менялся API, frontend приведён в соответствие;
- если менялось поведение, документация и UI-тексты обновлены;
- нет новых расхождений между backend и frontend по контракту.
